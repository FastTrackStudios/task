# The demo

Two companies, two servers, two iroh endpoints, one project across the
boundary. This is `examples/studio` — the tree the integration suite
reads and the four people it hires — planted on disk and served, so the
world the tests assert against is a world you can sign into.

```sh
just demo serve    # both servers — leave this running
just demo desktop  # in a second terminal: the desktop app against ACME
just demo web      # or the web app (:8766)
just demo ids      # each org's endpoint id
```

Every command plants the orgs on first use (idempotent); `just demo`
plants without serving, and `just demo fresh` wipes and replants.

The app boots **already signed in as Alice** — the demo script hands the
cast to debug builds via `TASK_DEMO_CAST`, the app signs in as its first
member, and the account switcher and the sign-out screen both offer the
rest of the cast one click each (Sam the employee, Casey the client).
The password behind every click is `correct-horse-battery-staple`; the
sign-ins are the real credential flow with it pre-filled, not a bypass.
Release builds ignore the variable entirely — no shipped binary can be
talked into a password sign-in nobody typed.

Everything lives under `~/.local/share/task-demo` and is throwaway.
`TASK_DEMO_ROOT` moves it.

## Which local world you want

There are two, and they answer different questions.

| | `just dev-seed` | `just demo` |
|---|---|---|
| shape | several orgs, one server, one process | one org per server, two servers |
| data | synthesised — 50 projects, albums, ffmpeg media | `examples/studio`, the committed studio disk |
| people | one owner with every role | four, each holding something different |
| federation | none | the point |
| use it for | eyeballing multi-org UI, lots of content | anything about two companies, grants, or the wire |

`dev-seed` is the bigger, richer single-server world. Use `demo` when
what you are working on involves an org boundary — sharing, admission,
peering, client access — because inside one process those all work for
reasons that will not survive being deployed. Both federation bugs this
repo has actually had were "it worked because both sides shared a
process".

## The cast

| who | org | holds | where |
|---|---|---|---|
| Alice | ACME Audio | owner | everything, including the guest list |
| Sam | ACME Audio | employee | the work, but cannot widen the guest list |
| Casey | — | client | `Deliverables`, read and comment, no download |
| Victor | VNT Video | owner | everything of VNT's |

All four use the same password. They are defined once, in
`apps/server/src/example_org.rs`, and the integration suite hires the
same four from the same list — so what `tests/integration/tests/people.rs`
proves about Casey is true of the Casey you can log in as.

Casey is the one to look at. `Comment` without `Download` is a client who
can review the mix and not keep it, and the `Deliverables` scope is the
difference between a client link and an org membership.

**One known gap, asserted on purpose.** Per-path access exists only in
Files. Every other lane — projects, tasks, notes, wiki — is gated by the
coarse permit table, which asks only "is this a validated user". So Casey
can list ACME's projects. `office.rs` asserts that deliberately, so
closing it is a decision someone makes and sees fail there rather than a
surprise.

## What is not done for you

The seeder plants trees and accounts, and adopts each org's own project
directories as File Roots named after their projects — that is what a
person would do first in the app anyway, and the review surface cannot
exist without it (video streams *renditions*, and renditions belong to
a root). It still does not offer or accept anything across the org
boundary: federation stays a call a signed-in person makes over the
wire, because baking it in would hide the half of the demo worth
watching.

```
acme-audio/files/Projects/Example Album
acme-audio/files/Projects/First Single - Example Client
vnt-video/files/Projects/Example Documentary - First Client, Second Client
vnt-video/files/Projects/Shared Project
```

Video deliverables are generated by ffmpeg at plant time into each
project's `Deliverables/` folder, so the project page's video opens the
review platform (mini player, expandable to the full review screen with
frame-anchored comments) out of the box.

## Endpoint ids

Each org binds its own iroh endpoint and its id is the whole address —
no host, no port, no certificate. `just demo ids` prints them; they are
also at `orgs/<slug>/iroh-endpoint-id` and in the server log at boot.

The id is stable across restarts because the key beside it is on disk
(`orgs/<slug>/iroh-key.ed25519`, 0600). That is what makes registering a
device against an id meaningful — an id with a per-boot lifetime would
make every registration a lie with a short expiry.

Losing that key loses the org's address, not its data. Every device
registered against it has to be re-registered.

### How they find each other with no internet

A deployed endpoint publishes itself to n0's DNS as it binds and is
dialled by bare id from anywhere. That needs the internet, which a demo
on a laptop may not have — so `just demo serve` sets
`TASK_IROH_PEER_DIR`, a directory both servers write their own address
into and read each other's out of.

It is a stand-in for discovery, sitting on the `MemoryLookup` seam iroh
already provides. Everything above it still dials by bare id and cannot
tell the difference — which is the property that matters, because it
means the demo exercises the same dialler a deployment runs
(`files::IrohRemotes`) rather than a test-only path.

Do not set it in a deployment. If you want to, what you actually want is
n0 discovery working, or a LAN address-lookup service.

## Ports

| | HTTP | iroh |
|---|---|---|
| ACME Audio | 18080 | its endpoint id |
| VNT Video | 9102 | its endpoint id |
| web app | 8766 | — |

`ACME_PORT`, `VNT_PORT` and `WEB_PORT` override the HTTP ones. The iroh
endpoints have no port to configure, which is the point of them.

HTTP is still there because the browser needs it: the web app speaks vox
over a WebSocket, and iroh's client half compiles to wasm but nothing in
this repo dials it from the browser yet. Server-to-server and
device-to-device are iroh only.

## The desktop app

`just demo desktop` launches the native app pointed at ACME
(`TASK_VOX_URL=ws://127.0.0.1:18080/vox` — the runtime knob native builds
read, see `crates/ui-core/src/vox_session.rs`). Same login as the web
app. One caveat, printed by the script too: a server previously chosen
in the app's Servers panel is persisted and silently wins over the env
URL — if the app connects somewhere unexpected, that is where to look.

**The traffic itself goes over iroh.** The URL is discovery and
fallback: the well-known doc now carries each org's iroh endpoint id,
and a native client that has one dials the org by bare id from its own
device endpoint (`crates/ui-core/src/iroh_transport.rs`), presenting the
session as per-call bearer metadata — the registration model, the same
wire the integration suite drives. The script sets `TASK_IROH_PEER_DIR`
so the app resolves ids to addresses the way the two servers resolve
each other's, with no internet. `TASK_VOX_FORCE_WS=1` pins the app back
to the WebSocket while the transport is young;
`tests/integration/tests/ui_iroh.rs` is the chapter that proves the
whole path with no URL configured at all.

To point either app at VNT instead, override the URL by hand:
`TASK_VOX_URL=ws://127.0.0.1:9102/vox` (desktop) or
`TASK_VOX_URL_WEB=ws://127.0.0.1:9102/vox` (web, baked at build time).

## What to try

The playground exists to exercise features against committed, throwaway
data — the same tree and the same four people the integration chapters
assert against, so anything you can do here has a test that names it.

- **Review a video.** `First Single` owes a "Lyric video"; its project
  page mounts the review platform's mini player on it, and the expand
  button opens the full review screen — scrub the filmstrip, comment at
  a timecode (signed as you), watch the marker land on the timeline.
  Every seeded video carries TWO versions (rough cut → final): open the
  version menu to pin v1 or compare them side by side. (The seeder
  already adopted the project's directory as a root; re-adopting
  another tree in place is still `files.adopt.in-place`,
  catalogue-first.)
- **Review the mix.** The "Single master" audio deliverable has a
  Review door beside Play: the same review surface with a waveform
  stage drawn from the peaks rendition — timecoded comments on a mix.
- **File feedback as work.** Hover any review comment and hit the
  check icon — it lands on the project's task board, titled by the
  note with the file and timecode riding along.
- **Upload into it, organise it.** Tags and favourites are views, not
  moves (`files.organise.manual`); a name collision on upload offers
  keep-both / replace / keep-existing (`files.write.upload`).
- **Create pages.** Projects, tasks, goals — every page lands in the
  org vault as plain markdown, and (since `project.vault.write-path`)
  through the Files API: the vault is itself a root from boot, so the
  page shows up in the catalogue like any other write.
- **Cross the boundary.** Admit VNT by its endpoint id, offer a folder,
  accept it on the other side — the `collaboration.rs` chapter, by hand.
- **Sign in as Casey.** One click from the account switcher — a client
  who can review `Deliverables` and not keep them, the sharpest
  demonstration of per-path access.

Wipe and start over with `just demo fresh`.

## Local telemetry

The server and the desktop app already carry the full
`architect-telemetry` pipeline — wide per-RPC spans (one context-rich
span per vox call, `LayerRouter::call_span`), logs, and metrics over
OTLP — gated on one variable: set `OTEL_EXPORTER_OTLP_ENDPOINT` and they
export, leave it unset and they are telemetry-free. The cluster sets it;
locally, the demo does:

```sh
just demo telemetry       # Grafana+Tempo+Loki+Prometheus in one container
just demo serve           # anything started while the collector is up attaches
just demo desktop         # the desktop app exports too — client and server
                          # halves of one RPC land as one trace
```

Grafana is at <http://127.0.0.1:3000> (anonymous admin — Drilldown →
Traces / Logs / Metrics). `just demo telemetry-stop` stops the container
and keeps its data; `docker rm task-demo-telemetry` wipes it.

Attachment is detection, not configuration: `serve`/`desktop` probe
:4318 and export only when a collector is actually listening, because an
exporter pointed at nothing retries noisily for the life of the process.
So the one rule is *collector first* — a server that booted before
`telemetry` came up needs a restart to attach. An
`OTEL_EXPORTER_OTLP_ENDPOINT` already in your environment always wins
over the probe. Ports move with `GRAFANA_PORT` / `OTLP_PORT`.
