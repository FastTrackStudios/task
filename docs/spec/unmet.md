# What is not met

Every rule the code does not satisfy, in one place, with what each needs.
Generated by hand and kept honest by `tracey query . uncovered` and
`tracey query . untested` — if this file and those disagree, they are
right.

As of the last update: **121 of 125 built-feature rules verified, 99 with
an implementation reference** (the six `doc.*` rules of
[`documents.md`](documents.md) are new: four verified, two visual). What
follows is the remainder — four rules — and two rules met in part. The 57 rules of
[`../../features/wiki/spec/wiki.md`](../../features/wiki/spec/wiki.md)
are tallied separately: **37 carry an implementation marker, 32 of those
are verified, 25 have neither** — the "declared, not built" section below
says which and why.

The five `wiki.promote.*` rules are new and all five land met: the
planner is `wiki_proto::promote` (unit-tested against both schema
dialects), the composition is `task wiki promote`, and
`tests/integration/tests/it/wiki_promote.rs` verifies all five over the org
router against the seeded Studio Research / Audio Production pair. One
honest caveat, recorded here rather than in a marker: a promotion is two
`write_page` calls with no transaction across them, so a crash between
them leaves the copy written and the source's back-reference missing.
The order is chosen so that is the recoverable direction (`--force`
repairs it) and the CLI says so when it happens; a genuinely atomic
promotion would need a multi-page write on the Pages service, which no
caller needs yet.

## Met, and not checkable by a test

### `project.definition.single`

> Exactly one definition of a project is in force.

What violates it is a *second* `ProjectInfo` appearing, which no run can
observe. The impl marker sits on the first one. `docs/spec/scenario-album.md`
says the same of this rule and of `project.capability.closed`.

There is a near miss worth recording: `Capability` genuinely does exist
twice, in `project-proto` and in `files-domain`, because neither crate
can depend on the other and there is no shared leaf. `project::conventions`
bridges them and carries a test that fails if either gains a member the
other lacks — see that module on why a duplication that cannot drift
silently is a different thing from a duplication.

### `doc.editor.typography` and `doc.properties.shared`

> Both editors read at Linear's measures … A note's properties use the
> task's property system.

Both are about how a surface looks, and no test in this repo renders CSS.
The impl markers sit on the one stylesheet (`doc_editor::DOC_CSS`) and on
the shared `PropertyRow` / chip classes the note panel now uses; checking
them is a screenshot against `http://localhost:8766/tasks/<id>` (the
seeded *Master review with the label*) and a vault note, desk and phone.

## Met in part

### `doc.editor.one`

> A task's description is edited with the same markdown editor as a vault
> note.

The same editor, keymap, catalog and typography — but the task body is a
plain buffer, and a note's editor carries more. Open, each its own piece
of work:

- **No live collaboration or presence in a task body.** A note's editor
  joins a per-file CRDT session; a task body commits whole-record updates,
  so two people typing in one description at once is last-writer-wins
  rather than merged. Joining the session would mean editing the task
  file's body region through the vault collab lane while `TaskService`
  owns the frontmatter — the race `doc.editor.body-only` exists to avoid.
- **No `[[` / `#` completion and no wikilink resolution in a task body.**
  The note view builds both from the vault's folder index; the issue page
  does not fetch it. A `[[link]]` typed in a description is kept and
  styled, but neither completed nor followed.
- **Attach files has no upload path.** `/attach` and ⌘⇧U insert a
  `[File name](url)` placeholder; a task has no File Root of its own to
  put bytes in yet. Image likewise inserts `![](https://)` to fill in.
- **The composer (`new_issue.rs`) still takes a plain description field**,
  committed with the new issue; only the issue page uses the editor.
- **Shortcut glyphs are the Mac's** (⌘⌥⇧) on every platform; the keys
  work with Ctrl elsewhere, but the menu does not say so.

### `files.access.role-baseline`

> What a caller may do is their org role united with their grants …
> Every lane checks.

Every lane checks, as the caller the gate resolved (`files::lane::caller`),
and `tests/integration/tests/it/app_store.rs` proves it over the router: a
member creates and saves, a client holding one granted folder is refused a
root and hears nothing of it on the live stream. The v1 `FilesService`,
which checked nothing per path, is deleted — there is one Files API. Three
things stay open, each its own piece of work:

- **Device identity is still per process.** The sync lane keys subscriptions
  and pins to `this_device()`; a restarted device reads back an empty
  subscription. A device principal does not reach the lanes yet.
- **Upload sessions are process-lifetime.** `pending` is now per person, but a
  server restart forgets open sessions (progress in a media root survives in
  the chunk store; a software root re-sends).
- **Roles are cached for ten seconds** (`memberships::FilesRoles::TTL`), so a
  revoked membership stops conveying on the Files lanes within that window
  rather than on the next request.

A `VersionId` carries a commit's leading 128 bits and resolves as a prefix
through the root's index, so the lanes cannot name or pin a commit that was
never indexed. Every commit the lanes write is indexed; only a commit placed
in the store by hand or by a replica ahead of its index is out of reach until
it is imported.

A software root's etag is `blake3:<hex>` of its bytes, since it has no chunk
store; `MediaService::read_content` cannot resolve one, so a pinned
`ContentRef` into a software root can say it moved but cannot fetch the old
bytes.

### `project.capability.conventions`

> Each capability declares the facets its work produces, the artifacts to
> ignore or absorb, its checkpoint cadence, its deliverable kinds, and the
> UI surfaces the project offers.

Facets and ignored artifacts exist and are verified. Checkpoint cadence
lives in `files_domain::cadence` and is not keyed by capability;
deliverable kinds and UI surfaces have no home at all. The marker covers
the half that exists and `project::conventions` says so in its module
docs rather than letting the marker imply the rest.

**This entry came back, and that was the right move.** ADR 0003 added
`Capability::{Session, Signal, Ignition, Keyflow}` — the names of the
four applications built on Task — and this file recorded the deliverable
kinds and UI surfaces half as filled on the strength of it: a project
could declare `keyflow`, and a surface could read that label and decide
to show a chart.

It was not filled. Those four variants brought no facets, no tool
layouts and no ignore patterns; every one of them mapped to an empty
slice in `files_domain`, so the two clauses this rule's implementation
actually covers had nothing to cover for them. What they supplied was a
name for a *consumer*, and a primitive that enumerates its consumers is
not a primitive — every app then waits on a Task release before it can
say a word about its own domain, and a sixth app cannot exist until the
enum admits it. [ADR 0004](../adr/0004-vault-assets-resources.md)
removed them from both `project-proto` and `files-domain`, and this
paragraph is the honest replacement.

What would actually meet the half that is missing: a capability that
declares deliverable kinds and surfaces has to be a kind of *work*, the
way `music-production` is — a claim about what tools wrote this tree,
paying for itself in the ignore layer and the facet map — with the
deliverable vocabulary hung off that. Which application opens the result
is resolved from the node kinds and asset shapes present, not from a
label Task maintains. Recording an honest gap is better than a
vocabulary that has to be released to describe someone else's domain.

## Regressed on purpose, and recorded rather than hidden

**A project page is not in the vault's index, and three surfaces lose
it.** ADR 0004's fourth root moved a project out of `vault/Projects/
<slug>.md` and into `<org>/projects/<slug>/project.md`, which is the
whole of what makes a project one thing in one place. The cost is
mechanical and falls where a vault id is the key:

- **`.base` views.** A `.base` executes against one vault id
  (`vault_live::sync::base_views`), and a project page is served under
  `project:<slug>` rather than `default`. A user's saved view filtering
  `type: project` over their vault therefore comes back empty. Nothing
  in this repository breaks — no `.base` file is committed anywhere —
  but a person's own vault may hold one, and it will go quiet rather
  than fail.
- **`search_vault` and `read_note`**, over MCP and in the app. Both are
  scoped to the org vault; a project page is not in it.
- **The vault's link graph.** A `[[wikilink]]` from a note to a project
  page no longer resolves through the vault's own index.

The replacement is a *reference*, and it is built rather than promised:
`NodeKind::Project` parses, and `node_homes::LocalHomes` resolves
`project:crescendum` (and `project:crescendum/track-two`) to the page on
the tier, across an org boundary, gated by a subscription.
`tests/integration/tests/it/projects_tier.rs` is the chapter. What is NOT
built is the vault-local half — a `[[…]]` in a note that means a project
— which needs the wikilink resolver to consult the tier the way it
consults the wiki tier. Recorded here rather than in a marker, because a
marker would imply the whole of "referenced as needed" is met and only
the cross-org half is.

**A project page's write does not reach the catalogue as a delta.**
`project.vault.write-path` binds `vault_live::PageSink` per *vault root*,
and `FilesBackend::adopt_vault` binds one for the vault. A project shelf
is adopted as a File Root by `adopt_knowledge_roots` but has no sink, so
its catalogue hears about a page save through the disk watcher on the
next sweep rather than synchronously on the write. The rule itself is
unaffected — it is a claim about the vault, every page still in the vault
still goes through the port, and `tests/integration/tests/it/vault_root.rs`
proves it with a task — but the *project* page lost a property it had.

Closing it needs `ProjectBackend` to write shelf-relative
(`save_page_at(<shelf>, "project.md")`) rather than tier-relative, so a
sink bound at the shelf root is the one the write finds. That is a
contained change and deliberately not folded into the move. Both entries that were here — cross-org
reach for the Assets tier, and the player reading a frozen song folder —
came from an intermediate draft of ADR 0004 that filed assets at
`<vault>/Assets/<Kind>/`, and both are closed by moving the tier out to
`<org>/assets/<group>/`. The section is kept, empty, because an empty
section somebody has to deliberately re-open is a better guard than a
heading that quietly disappears.

What closed them, for the record, since the first entry said plainly
what it would take:

> **What closing this needs:** a way for a subscription to publish a
> *subtree of the vault* under a name, materialised and served the way
> `resources/` is — which is a decision about what an org exposes, not
> a plumbing change.

That turned out to be the wrong shape of answer, and the right one was
smaller. The tier never needed to be inside the vault. It was put there
to obtain per-file CRDT, and per-file CRDT does not come from the vault
— it comes from a directory being **registered** on `vault::Backend` +
`GraphBackend` + `VaultCollab`, which the `wiki/` tier has demonstrated
from outside the vault since before any of this
(`features/org/org-proto/src/shelf.rs` argues it at length;
`wiki_editor_e2e::two_collab_sessions_converge_on_a_wiki_page` is the
evidence). So `assets/` became a sibling root, an asset group became an
`org_proto::Shelf` like a wiki, and everything the first entry listed as
missing followed from that one move:

| what was missing | what serves it now |
|---|---|
| a cross-org materialiser for assets | `wiki_live::materialize::refresh_shelf`, reached by `SourceKind::Assets` — the vault engine, local and remote alike, differing only in what one fetch may weigh. (It was a byte walker, on the belief that the engine carried markdown only. The engine hashes every file it meets; the walker's real difference was that it overwrote a subscriber's edits, which is what routing both cases through one call fixed.) |
| `links::NodeHomes` naming a path something serves | `node_homes::LocalHomes::locate` returns `assets/<group>/<slug>.md`, which is exactly what a subscription materialises |
| a test that the reach exists | `tests/integration/tests/it/song_library.rs` (both halves: whole shelf, and part of one), `demo_plant::the_planted_song_shelf_is_subscribable_across_orgs` |
| the assertion that pinned the gap | `tests/integration/tests/it/setlist.rs` — its `assert!(refused.is_err())` on a chart-library subscription is now `.expect("a chart library is a shelf, and a shelf is subscribable")` |

The second entry — **the player still reads the frozen song folders** —
closes for a different reason, and it is worth stating exactly rather
than claiming more than is true. `crates/player-ui`'s
`fetch_kf_manifest` fetches `GET /org/{org}/media/songs/<slug>/song.md`,
on the resources tier. That is still where a song's *media* lives and
still correct: ADR 0004 moves the song's **document** and leaves
`manifest.json` and the stems where they are, because they are imports
nobody types into. What made the entry a regression was that the
*document* had moved somewhere unreachable, so the two halves of a song
could no longer be brought back together across an org boundary. They
can: the document is on a subscribable shelf and the media is on the
tier `/media` serves. `tests/integration/tests/it/setlist.rs` asserts both
in one breath, which is the only way a tier rule is checkable at all.

**What is still open, and is not a regression.** `/org/{slug}/media/`
serves `resources/` and does not serve `assets/`. That is deliberate,
not an oversight: reach for a shelf goes through a *subscription*, which
is a thing an organisation takes on and can drop, where a media route is
an open door. A player that wants a foreign org's asset document reads
its own subscribed copy under `subscribed/<domain>/<group>/`. If a
direct route is ever wanted it is a decision to make on its own terms,
and it should be made in an ADR rather than by widening a handler.

## Not reachable from this harness

### `storage.query.reach`

> Every query a client makes is answerable from a browser.

A platform constraint rather than a behaviour: what would violate it is a
read path depending on a database engine that exists only on native

## Declared, not built

**`features/wiki/spec/wiki.md` — 26 of 57 rules.** The spec was written
ahead of the work; `tracey query . uncovered` now lists the ids below and
that is correct, not drift. The reference format the spec rests on is
`docs/adr/0002-wiki-reference-format.md`; the vocabulary is in
`CONTEXT.md`.

What exists: an org holds a set of wikis, each declaring visibility,
Editors, a proposer gate and an optional repository source in
`_state/wiki.json` (`wiki.many.*`, `wiki.access.visibility`,
`wiki.access.directory`, `wiki.boundary.no-subscribe`); subscriptions
that materialise a source and refuse what the source does not admit
(`wiki.subscribe.{reference,editability,local-copy,local-authority,
refresh,resolution,transitive,federated}`, `wiki.core.*`); the Edit lane and
repo-sourced wikis (below); and `wiki.ref.{format,block}`. What remains,
grouped:

- **Promotion, local presence and the rest of subscription** —
  `wiki.boundary.role`, `wiki.promote.*`, `wiki.local.mount`,
  `wiki.subscribe.{working-copy,no-ceremony,push,inherit}`.
  Local copies are meant to be editable jj working states under
  `Task/Wikis/<id>`, and a push from one is an Edit Request; today a copy
  is a plain materialised tree and the lane is reached over vox only.

  `wiki.subscribe.federated` now lands **met**: a wiki or an asset shelf
  on another server subscribes, refreshes and orphans through the same
  surface as a local one (`task_server::federated_orgs`,
  `wiki_live::source_peers`, `tests/integration/tests/
  cross_server_wiki.rs`). The line is size, not kind — a remote refresh
  is bounded by `materialize::REMOTE_FILE_LIMIT` and reports what it left
  behind — so a **project** does not cross as a subscription (it *is* its
  media; those bytes go by File Root and `offer`/`accept`, per ADR 0003)
  and a **Resource** library crosses too (Signal's patches and samples are
  manifests, which is what that tier is for). The bytes a manifest names
  are reached by offer, and `FederationService::resolve_content` rejoins
  the two halves in one call: a foreign `ContentRef` in, a local root and
  a path rebased onto the offered subtree out — or `None` for a file
  outside what was offered, which is the case a hand-written rebase gets
  wrong. A *reference* into
  another server's org resolves as well, from the copy the subscription
  left behind (`node_homes::LocalHomes`), and is refused without one —
  which is the rule `tests/integration/tests/it/setlist.rs` pins. A
  `project:` reference across a boundary is the one that still does not
  resolve, because a project does not cross as a subscription and there is
  therefore no copy to answer from.
- **Linking and references** — `wiki.link.*`, `wiki.ref.{picker,stamp,
  redirect}`: backlinks across wikis, rename repair from history, the
  editor's picker, staleness from the stamp, and the org-registry redirect.
  Rename repair has its local half: `VaultSync::move_file` rewrites the
  links *within the vault or wiki* that named a renamed page
  (`vault_live::relink`; pinned by `wiki_edits::
  a_rename_carries_the_links_that_named_the_page`). What `wiki.link.repair`
  still wants is the rest — across wikis and subscribers, driven by the
  page's recorded history rather than a scan, and itself a version.
- **Lifecycle** — `wiki.life.*`: adoption, signed handover, orphans.
- **Resources** — `wiki.resource.{not-a-wiki,addressing,no-annotations,
  layers}`; `wiki.resource.rights` is met by `scripture`, and
  `wiki.resource.subscribe` by `wiki_live::materialize::refresh_resource`
  (the core Bible is served from its publisher's `resources/bible` and
  refreshes into the subscriber's own corpus library).
- **The Edit lane, the peer half** — `wiki.edit.home`. The lane itself
  is built: `wiki_live::edits_backend` implements
  `wiki_proto::service::edits::Edits` over one org's wikis, an Edit
  Request *is* a `TaskInfo` row (`task_server::wiki_tracker`), and
  `wiki.edit.{request,tracked,editor,auto-approve,reviewable,rebase,
  claim,gate}` are implemented and verified in `wiki-live`'s unit tests,
  `tests/integration/tests/it/wiki_edits.rs` and `apps/server/tests/
  demo_plant.rs`. Not yet: a request opened on a *peer* reaching the
  home's Editors — the backend accepts only at the wiki's home, but no
  relay carries a request there. Also open: an org admin bootstrapping
  the first Editor over RPC. `Caller::is_org_admin` is the hook; the
  server's default caller answers `false` because the org lane has no
  admin role to consult (see `permits.rs`), so today the first Editor is
  the wiki's creator or the seed.
- **Resources** — `wiki.resource.*` and `wiki.core.*`, whose first
  subject is `scripture`'s read-only verse spine. Brings the licence and
  per-passage availability posture that `Translation` already models.
- **Repo-sourced wikis, the linked-account half** — `wiki.source.*` is
  built and verified. `wiki_live::repo_source` exports a path in a
  repository into the wiki root as a **working copy**: the live,
  collaboratively edited version, which every save (a direct
  `write_page`, an accepted Edit Request, an Editor's auto-approved
  edit, a mounted-folder edit) lands in and nothing pushes. The server
  fetches on a schedule and the seed plants `Docs` over
  `Repos/task-docs`. A sync updates only pages the working copy has
  not touched; a page changed on both sides is kept as it is here and
  named in `RepoSource::conflicts` (cleared by saving the page again or
  by its coming to match upstream). The set of local changes is derived
  from the pages against the exported base (`_state/repo_mirror.json`
  keeps a content hash per path; `Registry::local_changes`, `task wiki
  changes`, MCP `wiki_local_changes`). The repository is reached only
  by `Registry::push_changes` (`task wiki push --title …`, MCP
  `wiki_push_changes`): Editor only, one branch per wiki
  (`wiki/<slug>/<pusher>`), one commit holding every local change, one
  pull request, recorded as `RepoSource::pending`; a later push rewrites
  the same branch and request, and the sync that first sees the commit
  merged clears `pending`, after which the change list is empty on its
  own. Nothing enters `EditStatus::Landing` any more
  (`reconcile_landings` only settles rows an older server left there).
  On GitHub the push is the pushing Editor's own: the server asks the
  central issuer for the GitHub account linked to that person
  (`GET /oauth2/linked-token?provider=github`, bearer the credential
  they presented, granted under the `forge:github` scope), pushes with
  their token as author and committer (`<login>@users.noreply.github.
  com`) and opens the pull request as them; an Editor with no linked
  account is refused before anything is pushed
  (`wiki_repo::identity_for`). What still stands between this and the
  rule: the issuer side — `auth-server`'s social sign-in, account
  linking and `linked-token` endpoint — must be deployed, and Forgejo
  repositories still land with the deployment's `TASK_FORGEJO_TOKEN`,
  as the deployment, because no per-user Forgejo link exists. The web
  app has no changes/push surface yet; the CLI and MCP do.

Remove entries as their rules gain markers; the section goes when the
last does.

## Built since this file was written

**Sync in both directions, in the shipped path.** The engine could
always do it — `files-sync`'s suite proves edits flow both ways — but a
*daemon* could not: it dialled a coordinator and pulled, and mounted
nothing anyone could dial back. Since there is no push, that is a
one-way sync with no error to show for it. Three pieces closed it, and
`files-daemon`'s `tests/peering.rs` and `apps/server/tests/device_sync_e2e.rs`
are the chapters:

- The daemon binds its own endpoint and serves the replica lane on it
  (`files_daemon::peering`), so `files.topology.multi-server`'s "bytes
  move directly where two peers can reach each other" no longer requires
  one of them to be a server. Its endpoint key is its identity — one
  file, persisted, so a restart is the same machine at the same address.
- The daemon captures before it pulls (`start_capture` + the cadence
  pass in `tick`). It had been reconciling against a local store that no
  background work ever wrote to, so the missing direction would have had
  nothing to send even once it existed.
- The server sweeps its admitted devices (`apps/server/src/device_sync.rs`),
  reading `orgs/<slug>/admitted-devices` on every pass so admission and
  revocation take effect without a restart.

`SyncService` gained `roots()` — "what have you got" — which is what a
machine holding nothing has to start from, and what the server's sweep
enumerates. Enrollment tokens are gone rather than finished: the
transport is the credential, so there was nothing left to mint.

**Pairing, without a person carrying a hex string.** `enroll_device` and
`coordinator` on the Files sync lane: the machine's endpoint id goes to
the org and the org's comes back, on the authority of a member's own
sign-in — which is the strongest thing available and has a person behind
it. The desktop app does it once per launch after sign-in
(`crates/ui/src/device_pairing.rs`); `task files device pair` does it for
machines with no app to sign into. Enrolment is idempotent on the
endpoint (a reinstalled laptop is the same laptop), and revoking now
dismisses the endpoint rather than only flagging the row — a flag the
sync path never consults is a revocation the revoked machine does not
notice. `features/files/files/tests/sync_lane.rs` has the three.

**Installing it as a background service.** `fts-files-daemon install`
writes a launchd agent or a systemd user unit and loads it, and the
desktop app runs that on first start from the copy shipped beside it —
the "keeps syncing when the window is closed" half. `docs/sync.md` is
the operator's page, including what is still a paste (pairing) and where
the App Store sandbox blocks this (it may not write into
`~/Library/LaunchAgents`).

**A progress bar that moved for the wrong files.** `FileProgress::percent`
counted chunks, and the store links a large file whole — so a
multi-gigabyte take, the one file where a person actually needs the bar,
read 0% for the length of its transfer and 100% at the end. Bytes now,
chunks only as a fallback.

**`project.vault.write-path`** — the last unimplemented rule. The write
path is a port now: `vault_live::PageSink`, bound per vault root, with the
filesystem as the default. `FilesBackend::adopt_vault` makes the org vault
a File Root at server boot and binds a Files-backed sink; a page save is
then a Files write (atomic in the tree, catalogue delta, cadence hint) and
the on-disk result is unchanged. `tests/integration/tests/it/vault_root.rs`
is the chapter. The "one choke point" claim turned out to be optimistic —
`task`, `goal`, `milestone` and `workstream` wrote with `std::fs::write`
and every backend deleted and moved with `remove_file`/`rename` — and all
of those go through the port now.

**`files.device.ingest`** — a source is declared once and swept on a
timer, idempotent on a content hash, which is the one key that survives a
rename, a remount, a restart and a re-registration.
`tests/integration/tests/it/ingest.rs` is one test per item on that list.
That closed `scenario.album.ingest`, so all 25 stages are verified.

`vault.index.lookup`, `vault.index.parse-once`, `vault.index.incremental`,
`vault.write.granular` and the vault half of `storage.query.no-scan` were
all one missing structure. `vault_entity::index::PageIndex` is it, and
`features/vault/vault-entity/tests/index.rs` counts parses rather than
timing them, so the assertions are exact.

## Activity

[`activity.md`](activity.md) lands with fourteen rules; twelve are
verified by a test (see its table). What is short, rule by rule:

### `activity.actor` — met in part

The byline is the signed-in caller only for writes that come **through the
org router with a session**. Everything else is named by a fallback, and
the fallback is a guess:

- **Writes with no router caller** — the forge poll loop, an editor saving
  a task's markdown, the CLI writing the vault, the watch bridge's own
  HTTP lane, the in-process notifier transport — reach the hubs with
  nobody attached. A task change from one of these is bylined with the
  task's **primary assignee** when it has one (right for a claim, a guess
  for anything else), otherwise "Someone".
- **Projects have no author seam yet.** `ProjectService` is not wrapped,
  so every `project_created` / `project_updated` says "Someone". The fix
  is the same decorator `AttributedTasks` is.
- **Timers belong to the local owner.** The app starts timers for
  `timer_proto::local_owner_id(org)`, not the signed-in user. Over the
  router the gate's caller is noted per timer user, so a session started
  from the app is bylined correctly; one started by the CLI or the watch
  is "Someone", because the local owner id is no account.
- **The ledger is a window, not a record.** The caller is noted per entity
  for thirty seconds and read when the change arrives (milliseconds
  later). Two people writing the same task inside that window can be
  credited with each other's change; a create whose id the backend mints
  is matched through a `task:new` slot, which two concurrent creators can
  cross the same way. Making it exact needs the author on the event
  itself — `TaskEvent` carrying who — which is a proto change to every
  hub.
- **Edit coalescing is per task, not per person**: two people editing one
  description inside ten minutes make one `edited` line, credited to the
  first.

### `activity.ui.entity` — met, not checked by a test

The timeline and composer are built (`crate::activity::EntityActivity`,
mounted on the task page and the project page's Overview) but no test
drives the UI. What it rests on is verified — the entity and project
filters, comment recording, the threads RPCs — and the sentences are unit
tested; the component's own wiring is not. A browser check, or a Dioxus
render test once the shell has a harness for one, would close it.

### `activity.feed.server-written` — met, no verify marker

Held by construction: the permit tables grant only `list` and `events`,
and there is no write method on the trait to grant. `permits_cover_router`
proves the tables cover what the router mounts, which is the half that can
regress; there is no test that asserts the absence of a write.

### Not recorded yet

- **Milestones.** `milestone_created` / `milestone_updated` are in the
  vocabulary and the filter, but no pump reads the milestone hub.
- **A task moving between projects** is not a line of its own (the entry
  carries the new project; the move is silent).
- **Resubscribe gaps.** The pumps re-seed their before-state on every
  resubscribe, because the hubs replay nothing; a task created while a
  pump was detached is seen as already existing and gets no `created`
  line. Same for captures and projects.
- **Archived / deleted captures** record nothing; only captured and
  processed do.
- **Read state.** The feed has none: "Mark all read" on `/activity` marks
  the *notifications* queue read, which is the badge a person clears from
  there. A per-person "seen up to here" marker on the history is not
  built.

## Offline — the records side ([`offline.md`](offline.md))

Device storage is architect's now (path-patched to `../architect` until
it is tagged): crdt `turso` (`TursoPersistence`), architect-atom
`persist`/`turso` (`LocalRows`, `use_persisted_store_list`, `CallQueue`,
`Mutation::run_queued`, `TursoRows`). Task opens one `<data dir>/device.db`
for both (`crates/ui/src/device_store.rs`).

### `offline.outbox` — met

Timer start/stop/switch/log/edit/delete queue when the server is
unreachable (`TimerMutations` → `run_queued`), replay in order on
reconnect, refusals dropped and named. Verified by architect's queue unit
tests and `apps/server/tests/it/offline_queue_e2e.rs` (real Turso file,
"restart", real server). Modes have no service call yet, so nothing of
theirs queues. Gap: an offline-started timer's placeholder row is not in
the device copy (temp rows are not written back), so after a relaunch
it is invisible until the queued start lands.

### `offline.replica` — met in part

Every shared list (tasks, projects, goals, milestones, inbox,
notifications, activity, contacts, timer sessions, day plans) reads the
device copy first, stale-marked, and keeps it on a failed fetch. Not yet:
day **templates** (a date never viewed cannot be materialised offline),
members, and the feature-app stores (bookings, finance, …), which still
use the unpersisted hooks. The web backend is `localStorage`, guarded at
1.5 MB per list — IndexedDB is the target. Verified by unit tests over
memory and Turso backends; the hook itself (Dioxus) has no headless test.

### `offline.boot` — met, not checked by a test

A remembered principal (per server and email, `local_store`) plus the
token already in the token store opens the workspace when the auth dial
is unreachable (`auth::resolve_session`); orgs come from the discovery
cache. Checked by hand: stop `just demo serve`, relaunch, the shell opens
with "Offline — changes will sync". No UI harness drives it.

### `offline.visible` — met in part

The shell pill counts queued calls ("N changes waiting to sync") offline
and while syncing, and disappears when the queue drains. Not yet: unsynced
**documents** (the TEXT side's pending set) are not counted, and rows do
not carry a pending mark — tasks and captures become documents in step 3,
where the mark belongs.

### `offline.local` — met on desktop; iOS see below

The app hosts the backend in-process (`task_server::local_node::LocalNode`,
installed by `apps/desktop` through `crates/node-host`); `task_ui_core::node`
routes every org lane, `/server/vox` and discovery to it when the active
address is `local://this-device` (the native default with nothing
configured). Verified by `apps/server/tests/it/local_node_e2e.rs` and the
`task_ui_core::node` routing tests. Gaps:

- **HTTP-only surfaces.** A node has no HTTP listener, so what the UI
  reaches over plain HTTP rather than vox does not work locally: song media
  at `/media/…`, `/blobs/*` signed URLs, rendition URLs in the review
  player, and the deliverable download link (`pages/project_detail/
  deliverable.rs`). Vox media (`MediaService` chunks) works. Either a
  loopback listener for those routes or a webview custom protocol would
  close it.
- **The auth secret** is the dev default unless `TASK_AUTH_SECRET` is set
  — a node should mint its own per data root.
- **An org created after boot** over the node's `/server` lane is hosted
  at once but not bound on iroh until `LocalNode::bind` (the join path
  calls it) or the next launch.
- **iOS**: see the iOS note under `offline.peers`.

### `offline.peers` — met in part

Every native node binds each org's iroh endpoint (`iroh_host::start`, key
at `orgs/<slug>/iroh-key.ed25519`) and runs the device pull, so it is
dialable and dials. A device joins an org held elsewhere with
`LocalNode::join` (same slug + id, the peer admitted, this node bound) and
the peer's `enroll_device` (Settings → "Keep on this device", which runs
both halves over the session held on the host). Verified (two nodes, no
host) by `local_node_e2e`. **Documents move between nodes**: every node
serves the `DocPeer` lane (`vault_doc::peer`, gated on `docs/replica`,
which `HostEngine` grants an admitted host and the lane narrows to hosts
that keep content), and every sweep (`device_sync::sweep`, now started for
orgs joined after boot too) pulls each admitted peer's documents through
`doc_peer::pull_peer` — list, then a three-session pipe per document whose
file differs, through each node's own registry, so persistence, relay to
open editors and the write-behind all apply. A document made from the same
file on two nodes is one document (`vault_doc::seed_from_file`), so a
seeded or copied file exchanges rather than being refused as foreign.
Verified by `peer_docs_e2e` (two nodes, no host: a note, a task, a note
edited on both). Not yet: two nodes that each **edited** a file into a
document before ever exchanging hold two lineages and are left as they are
(counted as `doc_peer.foreign`, one `warn!` per sweep); deletes do not
travel (see "Deleted notes come back"); a peer is trusted with all of the
org's documents rather than per person. (`peer_docs_e2e` runs with
permissions enforced: the creator of an org is its admin — `create_org`
records the membership — and a joined org's person is a member.)

### Not started: step 3 (tasks and captures as documents)

The doc⇄markdown codec is in `features/vault/vault-doc` (TEXT side,
below) — `parse`/`render`/`merge_text` and `Replica`; `DocBody` takes a
`doc:` replica handle and edits its `body` (task-file separator
convention: `vault_doc::body::shown`). `offline.doc.create`/`materialise` for tasks and inbox items, and
`TaskService` writing through documents, are unbuilt.

## Offline — the text side ([`offline.md`](offline.md))

The codec and the device replica are `features/vault/vault-doc`
(wasm-clean, no Dioxus); the server half is `vault-collab` +
`apps/server/src/doc_guard.rs`; the shell's driver is
`crates/ui/src/doc_replica.rs`, used by the note editor
(`collab.rs`, `pages/note_view.rs`) and available to `DocBody`.

### `offline.doc.shape` — met for notes

Every vault-file doc is `body` + `props`; existing whole-file docs convert
on open. Tasks and captures get documents in step 3. Nested frontmatter
values are plain Loro values (a property merges as one unit, by key), not
nested containers. **Mixed versions:** a client older than this change
edits the legacy `content` text, which nothing renders any more.

### `offline.doc.replica` — met for notes

Persisted per device (the device database's `TursoPersistence`, org-scoped
keys; a `FilePersistence` directory if it cannot open; IndexedDB per org on
the web), never torn down offline, re-attached by the driver, durable
imports, acknowledgement-tracked. Verified by `offline_doc_e2e` and
`vault_doc::replica` unit tests. Gaps: two panes on the same note open two
replicas over one store (convergent, but double writes); the driver's
Dioxus hook has no headless test.

### `offline.doc.create` — met for notes, in part

`<space> n` with no server makes the note's document at once under a
device-chosen path (`Untitled 3f9a.md`) with an `id` prop, remembers it
locally, and it opens and edits offline; `open_collab` now accepts a path
with no file, and the first sync writes it. Not yet: the vault explorer
does not list device-created notes while offline (the folder index is the
server's; the device index is step 3's), and a note's deep link only opens
offline when it was created on this device. Opening an existing note
offline works when this device holds its document.

### `offline.doc.materialise` — met for notes

The server's mirror is rendered from the document, byte-stable for
unchanged docs (the previous file's untouched frontmatter lines are kept
verbatim); folder/watcher edits merge in as changes committed under an
`"outside edit"` message, three-way against `meta.flushed_at` for a doc
that was closed. `TaskService` still writes whole task files (step 3).
Commit messages are the only attribution — the person behind an outside
edit is not recorded.

### `offline.doc.access` — met in part

Every attach runs the file's write guard for the caller and the lineage
check; a refused document stays on the device unchanged and the editor
says "not shared — kept on this device". Not yet: read-only replicas (an
attach needs write), and the per-person refusal is not driven through
`DocSync` by a test (only `open_collab`'s, in `wiki_edits`).

### `offline.visible` — per document, in part

The note status line and the phone strip say "Not synced" while the
replica holds what the server has not acknowledged; `DocBody` shows the
same marker when bound. Not yet: the shell's global count does not include
unsynced documents.

### `offline.peers` — documents between nodes: what is left

Met for the common case (see `offline.peers` — met in part, above): a task
or note arriving from a peer shows up live (`task_sync`). Left: separately
edited lineages of one file, deletes, per-person access, and documents
moving before the sweep's next pass — a pull runs on the sweep's cadence
(60s, `TASK_DEVICE_SYNC_SECS`), not live; a standing session per open
document between nodes would make it live.

### Deleted notes come back

A device holding a stale document of a note deleted elsewhere recreates
the file on reconnect (`open_collab` accepts a missing path; the doc wins).
Deletion needs a document-level tombstone.

## Bugs found on the way

**Fixed — `FilesBackend::sync_ingest_path` stalled on repeated calls.**
Not the third call specifically: any call whose wakeups landed on the
runtime worker that was parked in `pollster::block_on` — tokio keeps a
woken task in the parking worker's own LIFO slot, where no other worker
steals it. `files::backend::off_worker` is the fix: sync store work
reached from a runtime thread runs on a scoped helper thread that has
entered the runtime but is not a worker of it, so wakeups go to the
injection queue. The ingest bridge and the vault page sink both use it.
`features/files/files/tests/sync_bridge.rs` is the regression test, in
all three runtime shapes.

**Two adopters, one vault.** `TASK_SERVER_VAULT_ROOT` makes every org in a
process share one vault directory, and the second backend to adopt it
would open a second store over the first's `.fts-files` — the shape that
hangs. `lane::vault` keeps one adopter per vault per process; the second
shares the first's binding, and `shutdown` releases it so a restart in
the same process adopts afresh.

## Running the suites

The integration suite is written for **nextest** (one process per test),
which is what CI runs. It also passes under plain `cargo test` now — the
device endpoint the sessions dial from is cached per runtime rather than
per process — but nextest is the reference. Two groups of tests boot
whole servers or sleep through real cadence windows and need more than
the default 4s budget; `.config/nextest.toml` gives `integration`,
`task-server` and `files::cadence` 10s/×3. The `task-server` e2e
binaries used to boot against whatever `TASK_DATA_ROOT` resolved to — on
a developer machine, the real `~/.task`, whose orgs they raced on and
once wrote adoption markers into. They now boot a sandboxed data root
seeded with `examples/studio` (`apps/server/tests/it/support/mod.rs`), so
the world they assert against is the repo's example studio and nothing
else.
