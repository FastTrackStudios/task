# What is not met

Every rule the code does not satisfy, in one place, with what each needs.
Generated by hand and kept honest by `tracey query . uncovered` and
`tracey query . untested` — if this file and those disagree, they are
right.

As of the last update: **117 of 119 built-feature rules verified, 93 with
an implementation reference.** What follows is the remainder — two rules,
down from three — and one rule met in part. The 57 rules of
[`../../features/wiki/spec/wiki.md`](../../features/wiki/spec/wiki.md)
are tallied separately: **32 carry an implementation marker, 27 of those
are verified, 25 have neither** — the "declared, not built" section below
says which and why.

## Met, and not checkable by a test

### `project.definition.single`

> Exactly one definition of a project is in force.

What violates it is a *second* `ProjectInfo` appearing, which no run can
observe. The impl marker sits on the first one. `docs/spec/scenario-album.md`
says the same of this rule and of `project.capability.closed`.

There is a near miss worth recording: `Capability` genuinely does exist
twice, in `project-proto` and in `files-domain`, because neither crate
can depend on the other and there is no shared leaf. `project::conventions`
bridges them and carries a test that fails if either gains a member the
other lacks — see that module on why a duplication that cannot drift
silently is a different thing from a duplication.

## Met in part

### `project.capability.conventions`

> Each capability declares the facets its work produces, the artifacts to
> ignore or absorb, its checkpoint cadence, its deliverable kinds, and the
> UI surfaces the project offers.

Facets and ignored artifacts exist and are verified. Checkpoint cadence
lives in `files_domain::cadence` and is not keyed by capability;
deliverable kinds and UI surfaces have no home at all. The marker covers
the half that exists and `project::conventions` says so in its module
docs rather than letting the marker imply the rest.

## Not reachable from this harness

### `storage.query.reach`

> Every query a client makes is answerable from a browser.

A platform constraint rather than a behaviour: what would violate it is a
read path depending on a database engine that exists only on native
targets. The integration suite is native, so it cannot observe the
violation. Checking it needs the scenario run once with a browser client,
which `docs/spec/scenario-album.md` already says.

## Declared, not built

**`features/wiki/spec/wiki.md` — 25 of 57 rules.** The spec was written
ahead of the work; `tracey query . uncovered` now lists the ids below and
that is correct, not drift. The reference format the spec rests on is
`docs/adr/0002-wiki-reference-format.md`; the vocabulary is in
`CONTEXT.md`.

What exists: an org holds a set of wikis, each declaring visibility,
Editors, a proposer gate and an optional repository source in
`_state/wiki.json` (`wiki.many.*`, `wiki.access.visibility`,
`wiki.access.directory`, `wiki.boundary.no-subscribe`); subscriptions
that materialise a source and refuse what the source does not admit
(`wiki.subscribe.{reference,editability,local-copy,local-authority,
refresh,resolution,transitive}`, `wiki.core.*`); the Edit lane and
repo-sourced wikis (below); and `wiki.ref.{format,block}`. What remains,
grouped:

- **Promotion, local presence and the rest of subscription** —
  `wiki.boundary.role`, `wiki.promote.*`, `wiki.local.mount`,
  `wiki.subscribe.{working-copy,no-ceremony,push,inherit,federated}`.
  Local copies are meant to be editable jj working states under
  `Task/Wikis/<id>`, and a push from one is an Edit Request; today a copy
  is a plain materialised tree and the lane is reached over vox only.
- **Linking and references** — `wiki.link.*`, `wiki.ref.{picker,stamp,
  redirect}`: backlinks across wikis, rename repair from history, the
  editor's picker, staleness from the stamp, and the org-registry redirect.
- **Lifecycle** — `wiki.life.*`: adoption, signed handover, orphans.
- **Resources** — `wiki.resource.{not-a-wiki,addressing,no-annotations,
  layers}`; `wiki.resource.rights` is met by `scripture`, and
  `wiki.resource.subscribe` by `wiki_live::materialize::refresh_resource`
  (the core Bible is served from its publisher's `resources/bible` and
  refreshes into the subscriber's own corpus library).
- **The Edit lane, the peer half** — `wiki.edit.home`. The lane itself
  is built: `wiki_live::edits_backend` implements
  `wiki_proto::service::edits::Edits` over one org's wikis, an Edit
  Request *is* a `TaskInfo` row (`task_server::wiki_tracker`), and
  `wiki.edit.{request,tracked,editor,auto-approve,reviewable,rebase,
  claim,gate}` are implemented and verified in `wiki-live`'s unit tests,
  `tests/integration/tests/wiki_edits.rs` and `apps/server/tests/
  demo_plant.rs`. Not yet: a request opened on a *peer* reaching the
  home's Editors — the backend accepts only at the wiki's home, but no
  relay carries a request there. Also open: an org admin bootstrapping
  the first Editor over RPC. `Caller::is_org_admin` is the hook; the
  server's default caller answers `false` because the org lane has no
  admin role to consult (see `permits.rs`), so today the first Editor is
  the wiki's creator or the seed.
- **Resources** — `wiki.resource.*` and `wiki.core.*`, whose first
  subject is `scripture`'s read-only verse spine. Brings the licence and
  per-passage availability posture that `Translation` already models.
- **Repo-sourced wikis, the linked-account half** — `wiki.source.*` is
  built and verified. `wiki_live::repo_source` exports a path in a
  repository into the wiki root as a **working copy**: the live,
  collaboratively edited version, which every save (a direct
  `write_page`, an accepted Edit Request, an Editor's auto-approved
  edit, a mounted-folder edit) lands in and nothing pushes. The server
  fetches on a schedule and the seed plants `Docs` over
  `Repos/task-docs`. A sync updates only pages the working copy has
  not touched; a page changed on both sides is kept as it is here and
  named in `RepoSource::conflicts` (cleared by saving the page again or
  by its coming to match upstream). The set of local changes is derived
  from the pages against the exported base (`_state/repo_mirror.json`
  keeps a content hash per path; `Registry::local_changes`, `task wiki
  changes`, MCP `wiki_local_changes`). The repository is reached only
  by `Registry::push_changes` (`task wiki push --title …`, MCP
  `wiki_push_changes`): Editor only, one branch per wiki
  (`wiki/<slug>/<pusher>`), one commit holding every local change, one
  pull request, recorded as `RepoSource::pending`; a later push rewrites
  the same branch and request, and the sync that first sees the commit
  merged clears `pending`, after which the change list is empty on its
  own. Nothing enters `EditStatus::Landing` any more
  (`reconcile_landings` only settles rows an older server left there).
  On GitHub the push is the pushing Editor's own: the server asks the
  central issuer for the GitHub account linked to that person
  (`GET /oauth2/linked-token?provider=github`, bearer the credential
  they presented, granted under the `forge:github` scope), pushes with
  their token as author and committer (`<login>@users.noreply.github.
  com`) and opens the pull request as them; an Editor with no linked
  account is refused before anything is pushed
  (`wiki_repo::identity_for`). What still stands between this and the
  rule: the issuer side — `auth-server`'s social sign-in, account
  linking and `linked-token` endpoint — must be deployed, and Forgejo
  repositories still land with the deployment's `TASK_FORGEJO_TOKEN`,
  as the deployment, because no per-user Forgejo link exists. The web
  app has no changes/push surface yet; the CLI and MCP do.

Remove entries as their rules gain markers; the section goes when the
last does.

## Built since this file was written

**Sync in both directions, in the shipped path.** The engine could
always do it — `files-sync`'s suite proves edits flow both ways — but a
*daemon* could not: it dialled a coordinator and pulled, and mounted
nothing anyone could dial back. Since there is no push, that is a
one-way sync with no error to show for it. Three pieces closed it, and
`files-daemon`'s `tests/peering.rs` and `apps/server/tests/device_sync_e2e.rs`
are the chapters:

- The daemon binds its own endpoint and serves the replica lane on it
  (`files_daemon::peering`), so `files.topology.multi-server`'s "bytes
  move directly where two peers can reach each other" no longer requires
  one of them to be a server. Its endpoint key is its identity — one
  file, persisted, so a restart is the same machine at the same address.
- The daemon captures before it pulls (`start_capture` + the cadence
  pass in `tick`). It had been reconciling against a local store that no
  background work ever wrote to, so the missing direction would have had
  nothing to send even once it existed.
- The server sweeps its admitted devices (`apps/server/src/device_sync.rs`),
  reading `orgs/<slug>/admitted-devices` on every pass so admission and
  revocation take effect without a restart.

`SyncService` gained `roots()` — "what have you got" — which is what a
machine holding nothing has to start from, and what the server's sweep
enumerates. Enrollment tokens are gone rather than finished: the
transport is the credential, so there was nothing left to mint.

**Pairing, without a person carrying a hex string.** `enroll_device` and
`coordinator` on the Files sync lane: the machine's endpoint id goes to
the org and the org's comes back, on the authority of a member's own
sign-in — which is the strongest thing available and has a person behind
it. The desktop app does it once per launch after sign-in
(`crates/ui/src/device_pairing.rs`); `task files device pair` does it for
machines with no app to sign into. Enrolment is idempotent on the
endpoint (a reinstalled laptop is the same laptop), and revoking now
dismisses the endpoint rather than only flagging the row — a flag the
sync path never consults is a revocation the revoked machine does not
notice. `features/files/files/tests/sync_lane.rs` has the three.

**Installing it as a background service.** `fts-files-daemon install`
writes a launchd agent or a systemd user unit and loads it, and the
desktop app runs that on first start from the copy shipped beside it —
the "keeps syncing when the window is closed" half. `docs/sync.md` is
the operator's page, including what is still a paste (pairing) and where
the App Store sandbox blocks this (it may not write into
`~/Library/LaunchAgents`).

**A progress bar that moved for the wrong files.** `FileProgress::percent`
counted chunks, and the store links a large file whole — so a
multi-gigabyte take, the one file where a person actually needs the bar,
read 0% for the length of its transfer and 100% at the end. Bytes now,
chunks only as a fallback.

**`project.vault.write-path`** — the last unimplemented rule. The write
path is a port now: `vault_live::PageSink`, bound per vault root, with the
filesystem as the default. `FilesBackend::adopt_vault` makes the org vault
a File Root at server boot and binds a Files-backed sink; a page save is
then a Files write (atomic in the tree, catalogue delta, cadence hint) and
the on-disk result is unchanged. `tests/integration/tests/vault_root.rs`
is the chapter. The "one choke point" claim turned out to be optimistic —
`task`, `goal`, `milestone` and `workstream` wrote with `std::fs::write`
and every backend deleted and moved with `remove_file`/`rename` — and all
of those go through the port now.

**`files.device.ingest`** — a source is declared once and swept on a
timer, idempotent on a content hash, which is the one key that survives a
rename, a remount, a restart and a re-registration.
`tests/integration/tests/ingest.rs` is one test per item on that list.
That closed `scenario.album.ingest`, so all 25 stages are verified.

`vault.index.lookup`, `vault.index.parse-once`, `vault.index.incremental`,
`vault.write.granular` and the vault half of `storage.query.no-scan` were
all one missing structure. `vault_entity::index::PageIndex` is it, and
`features/vault/vault-entity/tests/index.rs` counts parses rather than
timing them, so the assertions are exact.

## Bugs found on the way

**Fixed — `FilesBackend::sync_ingest_path` stalled on repeated calls.**
Not the third call specifically: any call whose wakeups landed on the
runtime worker that was parked in `pollster::block_on` — tokio keeps a
woken task in the parking worker's own LIFO slot, where no other worker
steals it. `files::backend::off_worker` is the fix: sync store work
reached from a runtime thread runs on a scoped helper thread that has
entered the runtime but is not a worker of it, so wakeups go to the
injection queue. The ingest bridge and the vault page sink both use it.
`features/files/files/tests/sync_bridge.rs` is the regression test, in
all three runtime shapes.

**Two adopters, one vault.** `TASK_SERVER_VAULT_ROOT` makes every org in a
process share one vault directory, and the second backend to adopt it
would open a second store over the first's `.fts-files` — the shape that
hangs. `lane::vault` keeps one adopter per vault per process; the second
shares the first's binding, and `shutdown` releases it so a restart in
the same process adopts afresh.

## Running the suites

The integration suite is written for **nextest** (one process per test),
which is what CI runs. It also passes under plain `cargo test` now — the
device endpoint the sessions dial from is cached per runtime rather than
per process — but nextest is the reference. Two groups of tests boot
whole servers or sleep through real cadence windows and need more than
the default 4s budget; `.config/nextest.toml` gives `integration`,
`task-server` and `files::cadence` 10s/×3. The `task-server` e2e
binaries used to boot against whatever `TASK_DATA_ROOT` resolved to — on
a developer machine, the real `~/.task`, whose orgs they raced on and
once wrote adoption markers into. They now boot a sandboxed data root
seeded with `examples/studio` (`apps/server/tests/support/mod.rs`), so
the world they assert against is the repo's example studio and nothing
else.
