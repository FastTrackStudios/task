# What is not met

Every rule the code does not satisfy, in one place, with what each needs.
Generated by hand and kept honest by `tracey query . uncovered` and
`tracey query . untested` — if this file and those disagree, they are
right.

As of the last update: **109 of 119 rules verified, 87 with an
implementation reference.** What follows is the remainder.

## Unimplemented — a feature is missing

### `files.device.ingest`

> A device uploads what it originates — camera roll, stills, voice memos
> — to a configured destination with no per-item action.

Nothing in the repository does unattended origination upload. The upload
lane is there and works; what is missing is the thing that watches a
camera roll and decides, idempotently across restarts and
re-registration, that a photo has not been sent yet.

Blocks `scenario.album.ingest`, which is the one scenario stage with no
verification.

### `vault.index.lookup`, `vault.index.parse-once`, `vault.index.incremental`

> Resolving a page by id is served from an index rather than by
> iterating the vault.

The vault spec's own preamble says these describe behaviour that does not
exist yet: `VaultEntityStore::get_by_uuid` resolves through `find` →
`list` → `scan`, so a lookup by id iterates every page and re-parses
every page of that type, discarding all but one.

This is one feature — an index over the vault, keyed by content so a
parse is reused until the bytes change — and the three rules are its
three properties.

### `vault.write.granular`

> A write takes no lock wider than the pages it modifies.

`VaultEntityStore` locks the whole vault per mutation. Same preamble,
same paragraph. Probably the same piece of work as the index, since both
turn on the vault having a structure rather than a page list.

### `storage.query.no-scan`

> No read path answers a query by walking the tree or by parsing every
> entity of a type.

True of Files, whose reads go through the catalogue. Not true of the
vault, for the reason above — so this rule is met on one side of the
system and not the other, and closing the vault index closes it.

## Unimplemented — a migration, not a feature

### `project.vault.write-path`

> The production vault becomes a File Root and all writes to it go
> through the Files API, markdown included.

One choke point: every vault page in the system is written by
`vault_live::mutate::write_atomic`, reached through `save_page` /
`create_page`, and every entity gets there through `VaultEntityStore`.
So this is that function's implementation, a write port for a Files
backend to be bound to, and a vault that has been adopted as a root — not
eighty call sites.

`project::write` was the last caller bypassing the choke point and no
longer does.

## Met, and not checkable by a test

### `project.definition.single`

> Exactly one definition of a project is in force.

What violates it is a *second* `ProjectInfo` appearing, which no run can
observe. The impl marker sits on the first one. `docs/spec/scenario-album.md`
says the same of this rule and of `project.capability.closed`.

There is a near miss worth recording: `Capability` genuinely does exist
twice, in `project-proto` and in `files-domain`, because neither crate
can depend on the other and there is no shared leaf. `project::conventions`
bridges them and carries a test that fails if either gains a member the
other lacks — see that module on why a duplication that cannot drift
silently is a different thing from a duplication.

## Met in part

### `project.capability.conventions`

> Each capability declares the facets its work produces, the artifacts to
> ignore or absorb, its checkpoint cadence, its deliverable kinds, and the
> UI surfaces the project offers.

Facets and ignored artifacts exist and are verified. Checkpoint cadence
lives in `files_domain::cadence` and is not keyed by capability;
deliverable kinds and UI surfaces have no home at all. The marker covers
the half that exists and `project::conventions` says so in its module
docs rather than letting the marker imply the rest.

## Not reachable from this harness

### `storage.query.reach`

> Every query a client makes is answerable from a browser.

A platform constraint rather than a behaviour: what would violate it is a
read path depending on a database engine that exists only on native
targets. The integration suite is native, so it cannot observe the
violation. Checking it needs the scenario run once with a browser client,
which `docs/spec/scenario-album.md` already says.
