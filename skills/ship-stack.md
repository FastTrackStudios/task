# Ship a stack (Task's Local CI gate)

Task's PR gate is split. **Your machine** runs the expensive half: the
prek pre-push hook runs `just ci-local`, which runs fmt, change files,
the static guards, and the clippy, wasm and tests that `cargo rail plan`
says the change affects, on the warm local target dir. When it's green,
the hook posts the **`Local CI`** commit status, with how long it took.
**GitHub** runs one free job on a PR, then the full suite once per merge
to main. PR jobs run on GitHub's free hosted runners; everything that runs
after code is on main (the post-merge suite, release commits, images, the
desktop cache) runs on THEBATTLESHIP's self-hosted pools, `task-main` and
`task-release`, whose target dirs stay warm. Their job gate refuses any
PR job: the repo is public.

One green run on the top of a stack vouches for every layer below it,
because the top's tree holds every layer's change. So: many small PRs,
one local run, every PR green.

Branch names, PR titles, change files and releases follow
[`release-workflow.md`](release-workflow.md). The commands below follow
the `gh-stack` skill (always `--auto`, `--json` and `--yes`, never the
interactive forms). Work in the main checkout and switch branches; a
worktree with its own `target/` costs a cold build.

## What runs where

| When | Workflow / job | Runner | What |
|---|---|---|---|
| `git commit` | prek pre-commit (`prek.toml`) | your machine | rustfmt, shellcheck, actionlint on the **staged** files |
| `git push` | prek pre-push → `scripts/ci-local-hook.sh` → `just ci-local` | your machine | the PR gate's expensive half; posts **`Local CI`** |
| PR into main | `PR / PR checks` (`pr.yml`) | free hosted, rustup + cargo-rail, no nix | fmt, change files, rail route cases |
| PR into main | `Release / Release guard` | free hosted | judges `release/pending` PRs only; passes otherwise |
| push to main | `CI` (`checks.yml`): Plan, Lint, Tests, Wasm, Dependency cache, **`CI passed`** | Lint/Tests/Wasm on THEBATTLESHIP `task-main` (warm target dir per kind); Plan, Dependency cache, `CI passed` free hosted | the full suite (tests narrowed by rail evidence), once per merge; a newer merge cancels the older run |
| PR into `release/**` | `CI` | free hosted, nix `.#ci` + a rust-cache per build kind saved on main | a hotfix: the full suite |
| release commit on main | `CI` (never cancelled) | THEBATTLESHIP `task-main`, the same dev target dirs as every merge | the full suite, every test; `release-tag` needs its `CI passed` |
| release commit on main | `Images` (+ `Deploy` / `Desktop cache` at the tag) | THEBATTLESHIP `task-release`: release-profile artifacts only (Deploy's own jobs, node binaries and release assets stay free hosted) | GHCR images; `release-tag` waits for them |
| `git pull` onto main | prek post-merge → `scripts/rail-evidence-hook.sh` | your machine, in the background | rail evidence for the new HEAD, so the next `ci-local` narrows |

**Main requires:** `PR checks`, `Release guard` and `Local CI` (ruleset
25572114). `just release-tag` separately requires `CI passed` on the
release commit.

**`just ci-local`, in order** (`scripts/ci-local.sh`):

1. **checks:** `ci-fmt`, `ci-changes <base>` (every touched crate has a
   `.changes/*.md`), `ci-versions` (one version everywhere), `ci-manifests`
   (Cargo.lock matches), `ci-architect-css` (the token sheet comes through
   the architect-ui link).
2. **plan:** `cargo rail plan` from the merge-base with origin/main, through
   `scripts/ci-rail-plan.py`. Local evidence is used if
   `just rail-evidence` recorded some for the base.
3. **tests** (the rail-selected filter), **clippy** (`--workspace`, when
   rail requires it), **wasm** (only the `.config/rail-wasm.json` packages
   rail selected).
4. A pass record for HEAD (when the tree is clean and no BASE was given),
   then `ci-local: green in 2m16s (checks 9s, plan 1s, tests 1m59s, …)`.

## Steps

### 1. Hooks installed

```bash
nix develop            # prek, cargo-rail, nextest, shellcheck, actionlint
just install-hooks     # once per clone: prek shims into .git/hooks
```

Done when `.git/hooks/pre-push` exists and starts `# File generated by prek`.
prek itself is the pinned release binary (`nix/modules/prek.nix`). Move it
to the newest release with `just prek-bump`, then run `just install-hooks`
again.

### 2. One concern per layer

```bash
git fetch origin && git switch main && git pull --ff-only
gh stack init <type>/no-issue-<slug>        # bottom layer, from main
# …commit…
gh stack add <type>/no-issue-<next-slug>    # next layer, on top
```

Put each layer's change in that layer. To fix a lower layer, check it out,
commit there, then `gh stack rebase --upstack` and `gh stack top`. A
rebase conflict is resolved in the layer it stops on, then
`GIT_EDITOR=true gh stack rebase --continue`.

Done when `gh stack view --json` lists the layers bottom-up, each with
its own commits.

### 3. Commit through the hooks

A commit runs rustfmt, shellcheck and actionlint on the **staged files
only**. A hook that rewrites a file fails the commit: `git add` the
rewritten file and commit again. Commit from inside `nix develop`, so the
hooks find their tools. Every crate a layer touches needs a change file in
that layer:

```bash
cargo rail change add <crates> --bump <none|patch|minor|major> -m "Fixed …"
```

Done when `cargo rail change check --since <layer's parent sha>` prints
`change files: ok` for every layer.

### 4. Local CI on the top

```bash
gh stack top
just ci-local
```

Done when it prints `ci-local: pass recorded for <top sha>` and then
`ci-local: green in …`. If it prints `the tree changed, so no pass
recorded` with a file list instead, commit or restore those files and run
it again. A red run is fixed in the layer that owns the failure: rebase
upstack and rerun on the top.

Run this BEFORE pushing. git opens the connection to GitHub before
pre-push runs, and a long run outlasts it. With the pass recorded, the
hook vouches instantly. Editing any tracked file while it runs leaves the
tree dirty, so it records no pass.

Expect about 2–3 minutes warm when CI inputs changed (`.github/**`,
Justfile, nix, `scripts/**`, nextest config: the full set). It's less
when rail narrows.

### 5. Push and open the PRs

```bash
gh stack submit --auto
gh stack view --json
```

Each layer's push posts `Local CI` to every open layer the top contains,
with the run's time in the description ("passed in 2m16s on THEBATTLESHIP:
checks 9s, …"). Fill each PR from `.github/pull_request_template.md`
(`gh pr edit <n> --title … --body-file …`), and register each PR with the
session's tracker (T3: `link_pull_request`).

Done when every layer head shows `Local CI: success`:

```bash
for n in $(gh stack view --json | jq -r '.branches[] | select(.isMerged | not) | .pr.number // empty'); do
  h=$(gh pr view "$n" --json headRefOid -q .headRefOid)
  printf '%s ' "$n"; gh api "repos/FastTrackStudios/task/commits/$h/statuses" \
    -q '[.[] | select(.context=="Local CI") | "\(.state): \(.description)"] | first // "none"'
done
```

A layer showing `none` was pushed from a tree that doesn't contain it, or
with uncommitted changes. Push again from the top. Or run the full suite
on GitHub for that branch, which posts `Local CI` when green:
`gh workflow run checks.yml --ref <branch>`.

### 6. Merge

**Normal:** when `gh pr checks <n>` shows `PR checks`, `Release guard` and
`Local CI` passing on every layer:

```bash
gh stack merge <top pr> --yes --squash      # all-or-nothing, bottom-up
gh pr merge <n> --squash                    # a single PR (one-layer "stacks" aren't stacked on GitHub)
```

A wake-up or notification that says the checks passed is a hint, not proof.
Read `gh pr checks` yourself before merging.

**Forced** (the user asked for it, or a required check can't be satisfied,
e.g. while a required check is being renamed): bottom-up, one PR at a time,
each only once the one below has merged and this one is retargeted to
`main`:

```bash
gh pr ready <n>
h=$(gh pr view <n> --json headRefOid -q .headRefOid)
gh api -X PUT repos/FastTrackStudios/task/pulls/<n>/merge-async \
  -f merge_action=direct_merge -f merge_method=squash -f sha="$h" -F bypass_rules=true
```

A squash merge rewrites the layer below, so a PR further up may report
`CONFLICTING`. Rebase the remaining layers onto the new main with
`SKIP=local-ci gh stack sync` (it pushes; the rebased heads have no
recorded pass and are force-merged next), then continue. A PR still
`MERGEABLE` needs no sync.

Done when `gh stack view --json` shows every layer `isMerged: true`.

**Renaming a required check** (a job name, or the `Local CI` context):
main's ruleset still requires the old name, so force-merge the change and
then swap the ruleset entry:

```bash
gh api repos/FastTrackStudios/task/rulesets/25572114 > /tmp/rs.json
jq '{rules: [.rules[] | {type} + (if .parameters then {parameters} else {} end)
  | if .type=="required_status_checks" then .parameters.required_status_checks
    |= map(if .context=="<old>" then {context:"<new>"} else . end) else . end]}' /tmp/rs.json > /tmp/rs-put.json
gh api -X PUT repos/FastTrackStudios/task/rulesets/25572114 --input /tmp/rs-put.json
```

### 7. Main is green

Each merge to main starts a `CI` run on the `task-main` pool: warm
target dirs, so it compiles what the merge changed, and Tests runs only
the tests the diff affects since the last commit whose tests passed
there (rail evidence in the pool's store). A newer merge CANCELS the
older run, so only the newest main is checked; a release commit's run
(`chore(release): …`) is never cancelled, because `release-tag` needs its
own `CI passed`. Anything that leaves the pools cold (a toolchain bump, a
lockfile overhaul, a wiped cache): run `just pre-warm-ci` (or
`just pre-warm-ci both <branch> fresh` before merging the bump) so the
pools build once, ahead of the merges. To look at the queue:

```bash
gh run list -b main -w checks.yml -L 5 --json databaseId,status,headSha
```

Done when the run on main's head commit has a green `CI passed`.
`just release-tag` requires it.

## Reference

**Escape hatches**
- `SKIP=local-ci git push`: push without local CI; the PR waits on
  `Local CI`. (`local-ci` is the prek hook id; `Local CI` is the status.)
- `gh workflow run checks.yml --ref <branch>`: the full suite on GitHub;
  posts `Local CI` when green.
- `just ci-local <base>`: a narrower run against another base. It records
  no pass, so it can't vouch for the commit.

**Making local CI cheaper**
- `just rail-evidence` on a clean main: rail then narrows docs and fixture
  changes instead of running everything.
- `just rail-cases`: rail's route pins (`.config/rail-cases.toml`; `PR
  checks` runs them too). Run it after editing `.config/rail.toml` or
  `.config/rail-wasm.json`.
- Changes to CI inputs (`.github/**`, Justfile, nix, `scripts/**`,
  nextest config) always run the full set, locally and after merge.

**GitHub's free runners** (4 vCPU, 16 GB RAM, ~14 GB free disk plus ~30 GB
once the image's unused SDKs are deleted)
- **Setup:** `hosted-nix-rust` (frees disk, installs nix with the FTS
  cachix, enters `.#ci`, restores the build kind's rust-cache) for Lint,
  Tests and Wasm. `rust-rail` (rustup + cargo-rail + just + the cargo
  dependency cache that main's `Dependency cache` job saves) for Plan and
  `PR checks`. Images and Desktop cache free disk and install nix inline.
- **Cache budget:** 10 GB of Actions cache for the repo, evicted LRU. Only
  main saves (`save-if` on main), one rust-cache entry per kind. The Tests
  entry (dependency codegen) is the big one. If runs start restoring
  nothing, check `gh cache list --sort size_in_bytes`. The usual cause is
  a new writer saving per branch and overflowing the budget.
- **Slow is expected:** the post-merge suite blocks no one. Only
  `just release-tag` waits on `CI passed` and on the Images build, so start
  a release once main's run is green.
- **Disk full on Tests or Images:** the free-disk step must run before the
  build. Check the `Disk` step's `df` output.
- WarpBuild ran Lint and Tests until 2026-10-23. It was dropped because the
  cost isn't worth it when nothing waits on the suite.

**False alarms**
- A failed or cancelled check from a run that a newer run on the same
  commit superseded: the newer run's result replaces it.
- prek hands a pre-push hook only the first pushed ref. The stack lookup
  covers the other layers, so this matters only outside a gh stack.
- Logs of a running GitHub job aren't downloadable until the whole run
  finishes; read step results with
  `gh run view <id> --json jobs` meanwhile.
